# G007: window order has ties

A window function whose result depends on row order (`row_number`, `lag`, `lead`,
`first_value`, `last_value`, `nth_value`) is ordered by columns that do not identify a row
within its partition. Rows that tie on the PARTITION BY and ORDER BY columns come out in
an arbitrary order, and the warehouse can pick a different order on every run.

This most often breaks a dedup: `qualify row_number() over (partition by customer_id order
by order_date desc) = 1` keeps an arbitrary order when a customer has two orders on the
same date. The model runs, its tests pass, and its values change between runs with no
change to the data.

Only plain columns count as tie-breakers: `order by date_trunc('day', updated_at)` can tie
where `updated_at` does not. first_value, last_value and nth_value are not reported when
the partition and order columns determine the value they return. G007 is not reported when
the window's input has unknown grain.

## Broken

```sql
select *
from {{ ref('orders') }}                  -- grain (order_id)
qualify row_number() over (
    partition by customer_id
    order by order_date desc
) = 1
```

## Fixed

Add a tie-breaker so the ORDER BY completes a key:

```sql
select *
from {{ ref('orders') }}
qualify row_number() over (
    partition by customer_id
    order by order_date desc, order_id desc
) = 1
```
