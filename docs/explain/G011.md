# G011: filter drops rows with nulls

Layer: **operator**, each join, filter, aggregate, window and set operation, checked against the keys of what it reads.

A condition that compares a null is unknown, and `WHERE` drops unknown rows. G011
reports two places where that drops rows the SQL looks like it means to keep.

**NOT IN over values that can be null.** If the subquery (or list) holds a single
null, `x not in (...)` is never true, so the filter keeps no rows at all. Cardinal
reports it unless the subquery's column is proven non-null: by a `not_null` test,
`meta.cardinal.grain`, or a `where ... is not null` in the subquery.

**WHERE on an outer join's null-filled side.** A left join keeps the left rows that have
no match and fills the right side's columns with nulls. A `WHERE` condition on those
columns is unknown on exactly those rows, so it drops them: the left join behaves as
an inner join.

Conditions that handle nulls on purpose are not reported: `is null`, `is not null`,
`coalesce(...)`, and `... or c is null`.

## Broken

```sql
select order_id
from {{ ref('orders') }}
where customer_id not in (select customer_id from {{ ref('blocked_customers') }})

select o.order_id, c.region
from {{ ref('orders') }} o
left join {{ ref('customers') }} c on o.customer_id = c.customer_id
where c.region = 'EU'          -- drops orders with no customer
```

## Fixed

```sql
select order_id
from {{ ref('orders') }} o
where not exists (
    select 1 from {{ ref('blocked_customers') }} b where b.customer_id = o.customer_id
)

select o.order_id, c.region
from {{ ref('orders') }} o
left join {{ ref('customers') }} c
  on o.customer_id = c.customer_id and c.region = 'EU'
```

If dropping the unmatched rows is what you want, write an inner join.
